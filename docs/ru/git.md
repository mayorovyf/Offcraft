# Git: ветки, интеграция и коммиты

[English](../git.md)

Правила Offcraft для изменений исходников, интеграции и публикации.

[Документация](index.md) · [Инструкции агентам](AGENTS.md)

## Ветки и правила интеграции

- `main` — стабильная ветка. Изменения попадают в неё только через запрос на включение изменений (PR) из `dev`, после проверки и рецензирования. В проекте с единственным разработчиком автор может выполнить ревью самостоятельно; одобрение другого пользователя GitHub не требуется. Прямые коммиты и прямая отправка изменений в `main` запрещены.
- `dev` — интеграционная ветка следующего выпуска и сборок для разработки. Не разрабатывайте и не создавайте коммиты непосредственно в ней; вливайте изменения из рабочих веток.
- Для каждой возможности создавайте `feat/<short-name>` от актуальной `dev`.
- Для исправлений создавайте `fix/<short-name>` от `dev`. Для независимого существенного исправления используйте отдельную ветку; исправления незавершённой возможности могут оставаться в её ветке `feat/*`.
- Для документации, обслуживания и рефакторинга используйте `docs/*`, `chore/*` и `refactor/*`.
- Используйте короткие английские имена в kebab-case: `feat/jsonl-control`, `fix/capture-release`, `docs/git-workflow`.
- Публикация рабочей ветки необязательна. Допускается локальное слияние в `dev` с последующей отправкой `dev`; публикуйте рабочие ветки, когда этого требует совместная работа.
- `release/*` и `hotfix/*` пока не входят в этот процесс. При необходимости явно введите правила работы с ними.

Небольшие изменения тоже требуют рабочей ветки. Эти правила применяются к дальнейшей работе; не переписывайте существующую историю ради её подгонки под них. Если `dev` или удалённый репозиторий отсутствует, согласуйте настройку репозитория до интеграции, а не подменяйте её молча веткой `main`.

### Самостоятельное ревью и защита ветки

- Перед слиянием разработчик просматривает полный diff PR, исправляет найденные проблемы и записывает выполненные проверки и ограничения. Ассистент может помочь с ревью; ответственность за принятие изменений остаётся у разработчика.
- Защита `main` на GitHub должна требовать PR, с `required_approving_review_count=0`, без обязательного одобрения владельцев кода и без обязательного одобрения последнего push. Сохраняйте действие защиты для администраторов и запреты force-push и удаления ветки. Ноль обязательных одобрений не разрешает прямой push и не отменяет проверку и самостоятельное ревью.
- Внешнее ревью приветствуется, но необязательно. После нового push просмотрите новые изменения и повторите затронутые проверки до слияния. Реальное блокирующее ревью GitHub и другие требования защиты разрешайте штатно; не обходите защиту.
- Меняйте защиту осознанно через настройки репозитория или `gh` только с разрешения. Не отключайте защиту и не используйте административный обход слияния ради заблокированного PR. При появлении других разработчиков явно пересмотрите политику одобрений.


## Последовательность работы

1. Осмотрите текущую ветку и рабочее дерево. Не переключайте ветки поверх чужих незавершённых изменений и не выполняйте автоматически stash, reset или очистку дерева.
2. Обновите `dev` и создайте рабочую ветку. Реализуйте изменения, создайте коммиты и выполните первоначальную проверку в ней.
3. До интеграции получите актуальную удалённую `dev`, влейте её в рабочую ветку, разрешите конфликты и повторите затронутые проверки. Не откладывайте проверку совместимости до PR в `main`.
4. Влейте полную проверенную рабочую ветку в `dev` коммитом слияния (`--no-ff`). Сохраняйте границу возможности; не заменяйте слияние копированием файлов, cherry-pick или squash.
5. Проверьте интегрированную `dev` на регрессии, аварии и взаимодействия. Следуйте [verification.md](verification.md) и приведённому ниже ограничению времени.
6. Откройте PR из `dev` в `main` для подробной проверки и рецензирования. Опишите изменения, выполненные проверки и известные ограничения. Единственный разработчик может выполнить ревью собственного PR; внешнее одобрение GitHub необязательно. Исправляйте замечания рецензии через рабочие ветки, вливаемые в `dev`.
7. После проверки, самостоятельного ревью и устранения реальных блокирующих требований разработчик может влить PR в `main`, не ожидая Approve другого пользователя. Собирайте выпуски из принятого состояния `main`.

Согласовывайте дополнительные слияния в `dev`, пока открыт PR выпуска: в PR также входят последующие коммиты `dev`.

### Ограничение времени проверки

Целевое время — 10–20 минут, жёсткий предел — **20 минут на весь цикл проверки**, а не на каждую команду. Выбирайте подходящие модульные регрессии и целевую дымовую проверку среды выполнения; не соединяйте короткие команды в многочасовой прогон. Более длительные калибровки или полные прогоны платформы/масштабирования требуют явного согласия пользователя. Остановитесь по достижении предела и сообщите о непроверенном поведении; прерванный или частичный прогон не является PASS или полной приёмкой. Не ослабляйте утверждения, квоты или пороги приёмки ради успешного прогона. Изменения только документации требуют проверки ссылок/содержимого, а не запуска Minecraft.

### Пример локальной интеграции возможности

Эти команды предполагают чистое рабочее дерево, удалённый репозиторий `origin` и существующую локальную и удалённую `dev`. Выполняйте каждый шаг осознанно; останавливайтесь при ошибках или конфликтах. Создавайте коммиты, выполняйте слияние и отправку только при наличии разрешения на эти операции в рамках задачи.

```bash
git status --short --branch
git fetch origin
git switch dev
git merge --ff-only origin/dev
git switch -c feat/jsonl-control

# Реализуйте и проверьте; добавляйте в индекс только относящиеся к задаче файлы.
# Заголовок коммита: feat(protocol): add JSONL control
# Тело коммита: перечислите каждое изменение, входящее в коммит.

# Обновите dev и проверьте совместимость до интеграции.
git fetch origin
git merge origin/dev
# Разрешите конфликты, завершите слияние и повторите затронутые проверки.

git switch dev
git merge --ff-only origin/dev
# Задайте заголовок Conventional Commit и полный список изменений ветки.
git merge --no-ff feat/jsonl-control
# Проверьте интегрированную dev до публикации.
git push origin dev
```

Если `--ff-only` или отправка отклонены, исследуйте расхождение истории. Получите обновления, согласуйте интеграцию и повторите затронутые проверки; не выполняйте принудительную отправку. Не переписывайте опубликованную историю `dev`/`main` и не обходите защиту веток. Этот пример не выполняет слияние в `main`; для этого нужен PR.

## Формат коммитов

Используйте Conventional Commits для обычных коммитов и коммитов слияния:

```text
<type>(<scope>)[!]: <description>

<body: полный список изменений>

[footer]
```

- **Тип обязателен:** `feat` (новая возможность), `fix` (исправление ошибки), `refactor` (структура без изменения поведения), `perf` (производительность), `docs` (документация), `test` (тесты), `build` (сборка/зависимости/упаковка), `ci` (автоматизация), `chore` (обслуживание) или `style` (только форматирование кода, не изменения интерфейса).
- **Область обязательна:** затронутая подсистема, например `client`, `protocol`, `ui`, `render`, `mcp`, `fabric`, `forge`, `neoforge`, `build` или `git`. Для сквозных изменений используйте `app`, а не перечисление всех модулей в заголовке.
- Пишите короткое английское описание в повелительном наклонении без точки в конце: `add`, `fix`, `preserve`, `remove`. Ориентируйтесь на заголовок не длиннее 72 символов; ясность важнее.
- Один коммит представляет одно логически связанное изменение. Не смешивайте возможность с несвязанным форматированием, обновлением зависимостей или чужими правками.
- **Тело обязательно:** перечисляйте каждое включённое добавление, исправление, изменение и удаление отдельными пунктами, включая код, тесты, документацию, сборку и конфигурацию. Описывайте изменения, а не только имена файлов или главную возможность. При необходимости указывайте обоснование и ограничения; сообщайте только о действительно выполненных проверках.
- Для несовместимых публичных контрактов или пользовательских форматов используйте `!` и завершающую строку `BREAKING CHANGE: ...`, объясняя миграцию. Обычный внутренний рефакторинг не требует этого маркера.
- Ссылайтесь на задачу в завершающей строке (`Refs: #123`, `Closes: #123`) только с реальным номером задачи.

Примеры заголовков:

```text
feat(protocol): add JSONL control
fix(render): preserve texture binding during capture
refactor(app): shorten Java package paths
docs(git): document branch and commit conventions
build(neoforge): update pinned loader version
ci(build): build development tags
```

### Описания коммитов слияния

- Используйте тот же формат `type(scope): description`, например `chore(git): merge JSONL control into dev`. Заменяйте стандартные заголовки `Merge branch ...` и сгенерированные заголовки слияния PR.
- Обязательное тело перечисляет каждое изменение, которое входящая ветка вносит всеми своими коммитами, а не только последним. До слияния осмотрите её историю и итоговую разницу с целевой веткой; исключите изменения, уже имеющиеся в целевой ветке.
- Включайте код, тесты, документацию, сборку, конфигурацию и удаления. Отдельно описывайте изменения разрешения конфликтов. Ссылка на ветку/PR или фраза «слияние ветки» не является списком изменений.
- Подготавливайте окончательные заголовок и тело слияния PR по тем же правилам; не полагайтесь на стандартные значения сервиса размещения репозитория.

## Теги и сборки

- После слияния PR помечайте тегом проверенный коммит `main` для выпуска. Для сборок разработки помечайте проверенную `dev`, но никогда незавершённую рабочую ветку.
- Формат выпуска: `v<major>.<minor>.<patch>`. Формат разработки: `v<major>.<minor>.<patch>-dev.<N>` для целевой версии, например `v0.2.0-dev.1`, `v0.2.0-dev.2`, затем `v0.2.0`. Это примеры, а не текущая версия проекта.
- Используйте аннотированные теги с описанием версии/назначения. Никогда не переносите опубликованный тег; для новой сборки используйте новый тег. Отправляйте только явно согласованный тег, а не все локальные теги.
- Коммит, тег и артефакт должны соответствовать друг другу. Тег не обновляет версии сборок или MCP. До тега обновляйте все объявления версии из раздела [Версионирование](development.md#версионирование) через рабочую ветку → `dev` → PR в `main` для выпусков. Имена готовых артефактов и общий каталог `dist/` описаны в том же руководстве.
- Создание коммита, создание тега, публикация тега и публикация выпуска — отдельные разрешаемые операции, а не автоматические шаги завершения задачи.
- Тег или успешная сборка не подтверждают работу игрового клиента, протокола, скрытого окна или всех загрузчиков. В примечаниях к выпуску различайте проверенное поведение, исторические наблюдения и непроверенные конфигурации.

### Текущая автоматизация

На момент переноса руководства в этой рабочей копии нет файлов GitHub Actions в `.github/workflows/`. Правила веток/тегов выше — политика команды, а не утверждение о настроенной защите веток, автоматических сборках разработки или публикации выпусков. Локальные команды сборки и среды выполнения описаны в [verification.md](verification.md).

## Подготовка первой публикации на GitHub

Подготовка не создаёт GitHub-репозиторий, не загружает файлы и не создаёт коммиты. URL, видимость и публикацию определяет владелец. Offcraft использует [лицензию MIT](../../LICENSE); включить её в первый коммит и сохранять уведомления об авторских правах/разрешении при распространении. Метаданные загрузчиков, Maven и MCP должны согласованно объявлять MIT; сторонние компоненты сохраняют собственные лицензии.

Для каталога без Git-истории инициализировать рабочую ветку из корня проекта:

```powershell
git init -b chore/github-publication
git status --short --untracked-files=all
git add --dry-run .
```

Версионируемый `.gitignore` исключает результаты сборки, `dist/`, проверочные изображения, run-каталоги загрузчиков/миры, кеши Gradle, Node-зависимости, настройки IDE, локальные env-файлы и форматы секретных ключей. Все три Gradle wrapper JAR явно сохраняются. `.gitattributes` нормализует исходники в LF, а Windows batch-скрипты извлекает с CRLF. Ignore-правила не удаляют уже отслеживаемые файлы и не заменяют проверку секретов/истории.

Перед первым коммитом:

1. Просмотреть каждый файл из dry run. Включить исходники, документацию, сборочные скрипты, wrapper-скрипты/JAR, метаданные, `LICENSE`, `.gitignore`, `.gitattributes`; исключить миры, профили, account tokens, экспорты запуска, логи и сгенерированные JAR.
2. Проверить секреты и слишком большие файлы; если секрет когда-либо попал в коммит, отозвать его до публикации и осознанно рассмотреть удаление из истории. Одного `.gitignore` недостаточно.
3. Выполнить затронутые проверки из [verification.md](verification.md). Сборочные JAR остаются в `dist/` и публикуются вложениями GitHub Release, не коммитятся в исходники.
4. Создавать первый коммит в `chore/github-publication` только с разрешения, с Conventional Commit заголовком и полным телом. Однократно создать `main` и `dev` на этом проверенном начальном коммите для bootstrap репозитория; последующие изменения идут по обычным правилам рабочая ветка → `dev` → PR в `main`. Не перезаписывать существующие ветки или историю.
5. Создать пустой GitHub-репозиторий с выбранной видимостью; не генерировать в нём второй README, `.gitignore` или лицензию. Добавить его фактический URL как `origin`, проверить remote и отправить только явно разрешённые ветки. Авторизацию хранить в Git Credential Manager или SSH, не в исходниках и не в remote URL с токеном.
6. Назначить `main` default branch; для проекта с единственным разработчиком настроить обязательный PR с нулём обязательных одобрений, действием защиты для администраторов и запретами force-push и удаления ветки. Внешнее ревью оставить необязательным, как описано выше. Версии/теги/релизы публиковать только с отдельного разрешения. Коммит этого руководства сам по себе не включает защиту веток или CI.

Подготовка проверяет только локальный набор кандидатов. После разрешения коммита проверить staged diff и историю до push; локальная проверка не доказывает отсутствие приватных данных в существующем remote.
